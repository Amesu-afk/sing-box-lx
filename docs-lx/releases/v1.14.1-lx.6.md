Two configuration-validation fixes. A typo in `tuic.udp_relay_mode` used to be accepted silently and mean `native`, so a node meant to relay UDP over QUIC quietly did not; it is now a load-time error naming the value and the two legal ones. A `masque` outbound with `profile: standard` and no `uri` used to report two different errors depending on `vhttp` — one of them about `vhttp`, not about the missing field; it now always reports the missing `uri`, with the URI shape to write. No new keys, no changed defaults, no wire changes.

Два исправления валидации конфигурации. Опечатка в `tuic.udp_relay_mode` молча принималась и означала `native` — узел, задуманный с UDP поверх QUIC, тихо работал иначе; теперь это ошибка при загрузке, с указанием значения и двух допустимых. Outbound `masque` с `profile: standard` без `uri` давал два разных текста в зависимости от `vhttp`, причём один — про `vhttp`, а не про отсутствующее поле; теперь всегда сообщается про `uri` и показывается ожидаемая форма URI. Новых ключей нет, дефолты и провод не меняются.

## 🔧 Changed

- Unchanged: configuration (no new keys), the wire format of `tuic` and `masque`, the defaults (an empty `udp_relay_mode` still means `native`, `masque.uri` still comes from the profile), the tag sets of desktop, router and AAR builds, the Go toolchain (1.26.8), the four submodules.
- Upstream base is unchanged — sing-box `v1.14.1`. Known drift at the cut: `upstream/stable` is 10 commits ahead, together with a `wireguard-go` bump to v0.0.7. The WireGuard changes require re-basing the `wireguard-go` fork submodule first, so the whole set is still deliberately left for a separate sync.

## 🐛 Fixed

### 🧹 `tuic.udp_relay_mode`: a typo is now a config error instead of silently meaning `native`

- Was: the value was matched against `native` and `quic` with nothing to catch anything else, so `"qiuc"`, `"Native"`, `"udp"` and every other value fell through to the documented default, `native`. A node written with a mistyped `quic` used a different UDP relay mode than intended and said nothing about it. The neighbouring `congestion_control` rejects its own typos with `unknown congestion control algorithm: <value>`, so one outbound behaved two different ways. This is upstream behaviour, present since the tuic outbound was added.
- Now: any value other than the two documented ones is rejected when the config is loaded — `unknown udp_relay_mode: <value> (expected native or quic)`. `sing-box check` exits non-zero with that text.
- Boundaries: an empty `udp_relay_mode` still means `native`, as documented. Setting both `udp_over_stream` and `udp_relay_mode` is still reported as the conflict it is — that check runs first, because two options set against each other is a clearer report than a typo inside one of them. ([SPEC 091](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/091-CONFIG_VALIDATION_TUIC_MASQUE/SPEC.md))

### 🧹 `masque`: `profile: standard` without `uri` — one error text regardless of `vhttp`

- Was: the `vhttp` value was resolved before `uri` was checked, so a `standard` outbound missing `uri` failed with `masque: vhttp h2 is not implemented for the standard profile` when `vhttp` was `h2`, and with `masque: uri is required for the standard profile` on `h3`, `auto` or an unset `vhttp`. Both statements were true, but the first one pointed at the wrong field: after changing `vhttp` the user hit the second error anyway. The `uri` text did not say what to put there either.
- Now: `uri` is checked first, so the same text appears for every `vhttp` — `masque: uri is required for the standard profile — set it to the server's CONNECT-IP request URI, e.g. https://<host>/.well-known/masque/ip/*/*/`. The value is sent verbatim as the Extended CONNECT request URI (nothing in it is substituted by the core), so the example uses the RFC 9484 full-tunnel form rather than invented placeholders.
- Boundaries: the h2-on-standard error is unchanged and still reported — only configs that do have a `uri` now reach it. The `cloudflare` profile, which supplies its own default `uri`, is untouched. ([SPEC 091](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/091-CONFIG_VALIDATION_TUIC_MASQUE/SPEC.md))

## 🐛 Исправлено

### 🧹 `tuic.udp_relay_mode`: опечатка теперь ошибка конфигурации, а не тихий `native`

- Было: значение сверялось с `native` и `quic`, и ничто не ловило всё остальное, поэтому `"qiuc"`, `"Native"`, `"udp"` и любое другое значение проваливались в документированный дефолт `native`. Узел, где `quic` написан с опечаткой, работал в другом режиме UDP-релея, чем задумано, и ничего об этом не сообщал. Соседняя опция `congestion_control` при опечатке отвечает `unknown congestion control algorithm: <value>` — один и тот же outbound вёл себя двумя разными способами. Это поведение апстрима, живущее с появления tuic-outbound'а.
- Стало: любое значение, кроме двух документированных, отвергается при загрузке конфига — `unknown udp_relay_mode: <value> (expected native or quic)`. `sing-box check` завершается ненулевым кодом с этим текстом.
- Границы: пустой `udp_relay_mode` по-прежнему означает `native`, как и описано в документации. Одновременно заданные `udp_over_stream` и `udp_relay_mode` по-прежнему сообщаются как конфликт: эта проверка стоит первой, потому что две заданные друг против друга опции — более внятный отчёт, чем опечатка внутри одной. ([SPEC 091](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/091-CONFIG_VALIDATION_TUIC_MASQUE/SPEC.md))

### 🧹 `masque`: `profile: standard` без `uri` — один текст ошибки независимо от `vhttp`

- Было: значение `vhttp` разбиралось до проверки `uri`, поэтому `standard`-outbound без `uri` падал с `masque: vhttp h2 is not implemented for the standard profile` при `vhttp: h2` и с `masque: uri is required for the standard profile` при `h3`, `auto` или незаданном `vhttp`. Оба утверждения верны, но первое указывало не на то поле: поменяв `vhttp`, пользователь всё равно упирался во вторую ошибку. Текст про `uri` при этом не говорил, что туда писать.
- Стало: `uri` проверяется первым, поэтому при любом `vhttp` появляется один и тот же текст — `masque: uri is required for the standard profile — set it to the server's CONNECT-IP request URI, e.g. https://<host>/.well-known/masque/ip/*/*/`. Значение уходит в запрос Extended CONNECT как есть (ядро в нём ничего не подставляет), поэтому в примере — форма полного туннеля из RFC 9484, а не выдуманные плейсхолдеры.
- Границы: ошибка про h2 на `standard` не меняется и по-прежнему выдаётся — просто теперь до неё доходят только конфиги, у которых `uri` есть. Профиль `cloudflare`, приносящий свой `uri` по умолчанию, не затронут. ([SPEC 091](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/091-CONFIG_VALIDATION_TUIC_MASQUE/SPEC.md))
