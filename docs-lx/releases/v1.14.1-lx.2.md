Hotfix for REALITY nodes with the `firefox` uTLS fingerprint on Xray-core v26.9.8 and later: the server requires the post-quantum `X25519MLKEM768` key share, and the uTLS library used so far carried it only in the Chrome presets, so `fp=firefox` nodes were silently forwarded to the camouflage site. The fingerprint is now Firefox 148 and passes on new and old servers alike; other non-Chrome fingerprints still lack the key share and remain rejected by new Xray. The release also stops a VLESS `encryption` handshake from hanging forever against a node that accepts the connection and then goes silent. Configuration, the wire format and the tag sets of desktop, router and AAR builds are unchanged; building from source now pulls a fourth submodule.

Хотфикс REALITY-узлов с utls-отпечатком `firefox` на Xray-core v26.9.8 и новее: сервер требует постквантовый key share `X25519MLKEM768`, а в использовавшейся библиотеке utls он был только у chrome-пресетов — узлы с `fp=firefox` молча уходили на камуфляжный сайт. Теперь отпечаток = Firefox 148 и проходит и на новых, и на старых серверах; остальные не-chrome отпечатки шар по-прежнему не несут и новыми Xray отвергаются. Заодно хендшейк `encryption` VLESS больше не виснет бесконечно на узле, который принимает соединение и молчит. Конфигурация, провод и наборы тегов desktop-, router- и AAR-сборок не меняются; сборка из исходников тянет четвёртый сабмодуль.

## 🔧 Changed

### 📦 Fourth fork submodule: `submodules/utls`

- Building from source still requires `git clone --recurse-submodules`, now for four submodules instead of three (`wireguard-go`, `sing-tun`, `gvisor`, `utls`).
- Unchanged: configuration, the wire format, the tag sets of desktop, router and AAR builds, and the Go toolchain (1.26.8).
- Upstream base is unchanged — sing-box `v1.14.1`. Known drift at the cut: `upstream/stable` is 5 commits ahead (systemd daemon reload after package installation, TestFlight/App Store publishing tooling ×3, "Bind network reset dispatch to manager lifecycle" in `route/network.go`). They were deliberately left out of this hotfix release and arrive with the next sync.

## 🐛 Fixed

### 🦊 REALITY with the `firefox` uTLS fingerprint failed on Xray ≥ v26.9.8

- Was: an XTLS/REALITY server from Xray v26.9.8 onwards accepts only a ClientHello carrying the hybrid `X25519MLKEM768` key share before `X25519`. The previous fix SPEC 083 put that share back into the hello, but in the `metacubex/utls` v1.8.7 library only the chrome presets carry it — `firefox` there was Firefox 120 without the hybrid. Nodes with `fp=firefox` (providers hand it out right in the link) were silently forwarded to the camouflage site, the client logging `reality verification failed`.
- Now: a fourth fork submodule `submodules/utls` (`Leadaxe/utls-lx` = `metacubex/utls` v1.8.7 plus the Firefox 148 preset and the reuse of a single X25519 key between the hybrid and the classical key share entries, both carried over from `refraction-networking/utls`). The name `firefox` now means Firefox 148; the ClientHello structure matches the original library. Configuration does not change.
- Verified on a stand: Xray v26.9.9 — `fp=firefox` passes (204), the pre-fix core — `reality verification failed`; Xray v26.7.28 and v26.7.11 — no regression; `fp=chrome` — no regression.
- Not covered: the remaining non-Chrome fingerprints (`safari`, `ios`, `edge`, `android`, `360`, `qq`; `random` and `randomized` partly) still do not carry the hybrid share in `metacubex/utls` and are rejected by Xray ≥ v26.9.8. That is unchanged and a separate decision. ([SPEC 086](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/086-UTLS_FORK_FIREFOX148/SPEC.md))

### 🧟 VLESS `encryption` handshake could hang forever

- Was: against a node that accepts the TCP connection and then goes silent, the `encryption` handshake (post-quantum, ML-KEM-768) waited for the server's reply in a blocking read with no deadline. Cancelling or timing out the dial context did not reach it, and the call stayed inside `DialContext` — including over XHTTP.
- Now: cancelling or timing out the dial context aborts the handshake and closes the connection. A handshake that completes at that same moment keeps its own connection; there is no double close; with a non-cancellable context nothing extra is started.
- Unchanged: behaviour against healthy nodes. ([SPEC 050](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/050-URLTEST_ZOMBIE_RUN_SURVIVES_RESTART/SPEC.md))
