Hotfix for issue #14: with an XHTTP node behind a CDN that resets HTTP/2 streams (`INTERNAL_ERROR`), the core could pin the CPU at 100 % until restart. The stream-reset error leaked out of the transport conn with the HTTP/2 library's own error type; any HTTP/2 client running *through* that outbound (DNS-over-HTTPS with `detour`, rule-set `download_detour`, a chained outbound) mistook it for its own stream error and spun in its read loop without touching the network. The type no longer leaves XHTTP, HTTP and gRPC-lite conns; log text and configs are unchanged.

Хотфикс issue #14: с XHTTP-узлом за CDN, который сбрасывает HTTP/2-стримы (`INTERNAL_ERROR`), ядро могло держать 100 % CPU до перезапуска. Ошибка сброса выходила из транспортного conn'а типом самой HTTP/2-библиотеки; любой HTTP/2-клиент, работающий *сквозь* этот аутбаунд (DNS-over-HTTPS с `detour`, rule-set `download_detour`, цепочка аутбаундов), принимал её за ошибку своего стрима и крутился в цикле чтения, не обращаясь к сети. Тип больше не выходит из conn'ов XHTTP, HTTP и gRPC-lite; текст логов и конфиги не меняются.

## 🐛 Fixed

### 🔥 100 % CPU until restart with XHTTP behind a CDN that resets streams

- Was: after the CDN reset an upload/download stream, two HTTP/2 read loops sat in `runnable` at 100 % of a core each, with zero syscalls, until the process was restarted. The previous breaker/backoff changes (lx.29, lx.30) throttled reconnects but did not touch this loop.
- Cause: the XHTTP conn returned the reset as an `http2.StreamError` value. A consumer that is itself an `x/net` HTTP/2 client over TLS on top of the outbound gets that error made sticky by `crypto/tls`, and its read loop treats it as a per-stream error and continues forever.
- Now: `StreamError` is replaced at the conn boundary by an opaque error with the same text and no unwrap; the consumer's read loop exits on the first error and the request fails immediately. Applied to the XHTTP `stream-one` / `stream-up` / `packet-up` conns, to the HTTP transport conn and to gRPC-lite.
- Unchanged: config, wire format, the `connection download closed: stream error: stream ID N; INTERNAL_ERROR; received from peer` log line, the lx.29/lx.30 breaker and `GetBody` retry.
- Not affected: plain TCP/UDP relays through the outbound (the error only ended the copy there).
- Regression test reproduces the spin: 13 million body reads in 3 s without the fix, ≤16 with it. (SPEC 082)

## 🐛 Исправлено

### 🔥 100 % CPU до перезапуска с XHTTP за CDN, который сбрасывает стримы

- Было: после сброса upload/download-стрима со стороны CDN два цикла чтения HTTP/2 висели в `runnable` по 100 % ядра каждый, с нулём сисколлов, до перезапуска процесса. Предыдущие breaker/backoff (lx.29, lx.30) ограничивали переподключения, но этот цикл не трогали.
- Причина: XHTTP-conn возвращал сброс значением `http2.StreamError`. Потребителю, который сам является HTTP/2-клиентом `x/net` поверх TLS над аутбаундом, `crypto/tls` делает эту ошибку залипшей, а его цикл чтения считает её ошибкой своего стрима и продолжает бесконечно.
- Стало: `StreamError` на границе conn'а подменяется непрозрачной ошибкой с тем же текстом и без unwrap; цикл чтения потребителя выходит на первой ошибке, запрос падает сразу. Применено к XHTTP-conn'ам `stream-one` / `stream-up` / `packet-up`, к conn'у HTTP-транспорта и к gRPC-lite.
- Не меняется: конфиг, провод, строка лога `connection download closed: stream error: stream ID N; INTERNAL_ERROR; received from peer`, breaker и повтор через `GetBody` из lx.29/lx.30.
- Не затронуто: обычные TCP/UDP-relay через аутбаунд (там ошибка лишь завершала копирование).
- Регрессионный тест воспроизводит спин: 13 млн чтений тела за 3 с без фикса, ≤16 с ним. (SPEC 082)
