Hotfix for REALITY nodes on Xray-core v26.9.8 and later: the server now requires the post-quantum `X25519MLKEM768` key share in the ClientHello and silently forwards anything else to the camouflage site, which the client reports as `reality verification failed`. The core used to strip that key share itself, a leftover from an old uTLS version; it no longer does, and the authentication key follows the server's choice. `chrome` fingerprints (the default) work again against new and old Xray alike; fingerprints other than Chrome do not carry the key share and stay dead on new servers, exactly as with Xray's own client.

## 🐛 Fixed

### 🔐 REALITY nodes on Xray ≥ v26.9.8 failed with `reality verification failed`

- Was: every REALITY node behind Xray-core v26.9.8 / v26.9.9 stopped working; no server-side error, the connection was transparently forwarded to the camouflage `dest`, the client logged `reality verification failed`. Servers up to v26.7.28 were unaffected.
- Cause: the REALITY server now rejects a ClientHello without an `X25519MLKEM768` key share placed before the optional `X25519` one. The Chrome fingerprint carries it, but the core removed it from `supported_groups` and `key_share` before the handshake — a workaround for uTLS 1.7.2, which could not tell the hybrid's X25519 key from the plain one when deriving the authentication key. With the current uTLS the keys are kept separately, so the workaround had nothing left to fix.
- Now: the key shares are sent as the fingerprint defines them (`GREASE, X25519MLKEM768, X25519` for Chrome). The authentication key is derived from the plain `X25519` share when present, otherwise from the X25519 half of the hybrid — the same order the server uses.
- Verified on a local stand against Xray v26.9.9 (fails before, HTTP 204 after) and against v26.7.28 and v26.7.11 (all fingerprints work before and after — no regression on old servers).
- Unchanged: config, `fingerprint` values, servers older than v26.9.8.
- Not covered: fingerprints other than the `chrome` family (`firefox`, `safari`, `ios`, `edge`, `android`, `360`, `qq`, `random` in 4 of 5 cases, `randomized` about half the time) do not carry the hybrid share and are rejected by Xray ≥ v26.9.8 — the same as with Xray's own client. Use `chrome` for REALITY; LxBox substitutes it on its side. (SPEC 083)

### ✅ REALITY client version 26.3.27 confirmed against Xray v26.7.11

- The fix shipped since lx.22 that declares client version `26.3.27` (Xray's default `minClientVer` since v26.7.11) is now field-verified on the same stand: HTTP 204 with the fix, silent forward to `dest` with the upstream `1.8.1`. (SPEC 053)
