Two changes for REALITY nodes. Configuration otherwise unchanged; the wire format, the tag sets of desktop, router and AAR builds and the Go toolchain are unchanged.

## 🆕 What's new

### 🔑 `tls.reality.key_share`: hybrid or classical REALITY ClientHello, per node

- Background: since the hybrid `X25519MLKEM768` key share went into the REALITY ClientHello (required by Xray ≥ v26.9.8), the hello is 1720 B for `chrome`, 1885 B for `firefox`, 1533 B for `safari` — always two TCP segments. On some mobile networks that first flight is silently dropped (TCP established, ClientHello retransmitted, no answer, ~15 s timeout), while the classical 594 B hello passes. Xray's own client hits the same wall on such networks.
- `""` (unset): as the fingerprint carries it — `chrome` / `firefox` / `safari` send the hybrid share, `edge` / `ios` / `android` / `360` / `qq` send X25519 only. Unchanged behaviour.
- `"classical"`: `X25519MLKEM768` removed from `key_share` and `supported_groups` — the classical hello. **Only Xray servers older than v26.9.8 accept it**; newer ones reject the node silently (`reality verification failed`). Reduces post-quantum protection.
- `"hybrid"`: the hybrid share is required. On a fingerprint that has none (`edge`, `ios`, …) the handshake fails at once with `reality key_share "hybrid": fingerprint Edge 85 carries no X25519MLKEM768 key share`, instead of the server's silent rejection that looks like a wrong key. On `chrome` / `firefox` / `safari` it changes nothing.
- Any other value is a config error at load time. No automatic fallback between the two: on the affected network a server stays unreachable for about a minute after a hybrid attempt, so a retry would not help.
- For a new server on such a network the remaining levers are `record_fragment` (see below) and a `detour`. ([SPEC 089](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/089-REALITY_KEY_SHARE_OPTION/SPEC.md))

## 🔧 Changed

- Unchanged: configuration apart from the new key, the wire format, the tag sets of desktop, router and AAR builds, the Go toolchain (1.26.8), the four submodules.
- Upstream base is unchanged — sing-box `v1.14.1`. Known drift at the cut: `upstream/stable` is 10 commits ahead — the 5 already deferred in lx.2/lx.3 (systemd daemon reload, TestFlight/App Store tooling ×3, network reset dispatch) plus 5 new ones (implicit default DNS server/outbound initialize stage, command client cancellation, initial WireGuard handshake for domain peers, API dashboard default HTTP client, a docs fix) together with a `wireguard-go` bump to v0.0.7. The WireGuard changes require re-basing the `wireguard-go` fork submodule first, so the whole set is deliberately left for a separate sync.

## 🐛 Fixed

### ✂️ `fragment` / `record_fragment` did nothing on REALITY nodes

- Was: the REALITY client built its uTLS connection on the bare socket, bypassing the fragmentation wrapper that plain uTLS and standard TLS clients get. Both options were accepted by the config and silently ignored; the automatic `record_fragment` under `detour` (lx.19, SPEC 060) never reached REALITY either. This is upstream behaviour, not a regression of the fork.
- Now: REALITY takes the same wrapper as the uTLS client. With `record_fragment` the REALITY ClientHello goes out as several TLS records (two for a single-label SNI), with `fragment` as several TCP writes; without either flag — one record, as before. No new keys.
- Not a promise against DPI: whether splitting the first flight helps on a network that drops it depends on that network. Verified on the wire in tests; a field run on the affected network is pending. ([SPEC 088](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/088-REALITY_FRAGMENT_BYPASS/SPEC.md))

### ✂️ `fragment` / `record_fragment` на REALITY-узлах ничего не делали
