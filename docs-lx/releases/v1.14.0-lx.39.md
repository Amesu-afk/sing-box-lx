### 🛰 UDP through SOCKS5 proxies that answer `0.0.0.0` / `::`

- Was: a `socks` outbound (version 5) whose server replies to UDP ASSOCIATE with `0.0.0.0:port` or `[::]:port` — most public proxies, any server behind NAT — carried TCP but no UDP at all: DNS over UDP, QUIC, calls, games. - Now: an unspecified or empty relay address is replaced with the proxy server address from the config (IP or domain, resolved by the same dialer that made the control connection) and the port from the reply; a concrete address in the reply is used as is. A reply with port 0 is reported as a handshake error instead of being dialed. Only `version: 5` UDP is touched; TCP, BIND and `udp_over_tcp` paths are unchanged.
- Verified: unit tests on a recording dialer (the relay is dialed at the server address for IPv4/IPv6 unspecified replies and for domain servers; concrete replies untouched; port 0 rejected), the outbound seam, a live loopback relay round trip, race detector clean. A sentinel test pins the upstream library's current behaviour and flags the moment upstream fixes it itself.
- Unchanged: configuration, the `socks` inbound (server side), socks4/4a, `udp_over_tcp`, LxBox and the launcher. Field confirmation on the reporter's proxies is still open: the diagnosis was made from the code, not from a capture. (SPEC 085)
